# Design: Living Project Brief MVP

Generated by office-hours on 2026-05-10
Status: APPROVED
Mode: Startup

## Problem Statement

PM-like consultants and engagement managers on messy consulting projects lose project context across meetings, transcripts, emails, notes, deliverables, stakeholder asks, and analysis threads. The pain is strongest when one person is coordinating several projects or workstreams and is expected to remember decisions, requirements, priorities, country-specific needs, and follow-ups.

The current product should not be framed as a generic project management agent. The sharper problem is that the official understanding of a project decays after every meeting unless a human manually updates it.

## Demand Evidence

The strongest evidence so far is founder-user behavior:

- Taro built and uses a local repo-based agent for the Leadabeelity project.
- The existing workflow pulls from Blue Dot transcripts, Notion notes, colleague emails, Teams messages, project documents, and local memory files.
- Leo, Taro's manager, asked for a complete list of all Leadabeelity use cases discussed across workshops. Taro forwarded the request to the agent and sent back the answer.
- The agent generated a first PRD from accumulated project context, decisions, requirements, and contacts.
- Alessio asked whether the client had mentioned meals in the database or only foods. Taro asked the agent, which checked transcripts, working memory, `product.md`, and related context.
- Some colleague requests are handled by direct copy/paste into the agent and copy/paste back, with no extra expert interpretation from Taro.

This is not yet market proof. The current pattern is closer to proxy usage: colleagues route questions through Taro, and Taro routes them through the agent. The next proof is whether users still trust and use the product when Taro is no longer the trust wrapper.

## Status Quo

Without the agent, a PM-like consultant recovers project context by:

- Searching meeting transcripts in tools like Blue Dot.
- Reading summaries of many separate meetings.
- Checking Notion notes and project documentation.
- Searching or asking for colleague emails.
- Asking teammates on Teams what was decided or remembered.
- Copying transcripts into ChatGPT or Claude and then manually adding missing context from memory.

The real competitor is not only manual search. It is ChatGPT or Claude plus a human who remembers the project.

ClickUp Brain and Notion AI are also relevant competitors, but they are workspace-first: AI sits on top of the structure the team maintains. The proposed wedge is memory-formation-first: the product actively turns messy evidence into an official, reviewable project brief.

## Target User And Narrowest Wedge

The initial target user is not every project manager. The sharper ICP is:

> A PM-like consultant, engagement manager, delivery lead, or project coordinator who owns coordination across multiple workstreams, countries, stakeholders, meetings, analyses, and junior analysts.

The strongest example is Taro acting as de facto PM on Leadabeelity and other multi-stakeholder consulting projects, where human memory is overloaded by four or more concurrent projects.

The narrowest wedge:

> Keep a living project brief updated after every meeting.

The initial product promise:

> After every meeting, source drop, or important email, the product proposes updates to the official project brief. The user approves, edits, or rejects them. Later, the team can ask what happened, what was decided, and what exists, with grounded answers.

## Premises

1. The strongest wedge is not a generic project management agent; it is a living project brief that updates from meetings, emails, notes, and files, with human approval.
2. The first user is a PM-like consultant or engagement manager coordinating messy multi-stakeholder projects across many meetings and workstreams.
3. The product must beat the real status quo: ChatGPT or Claude plus a human who remembers the project.
4. The next proof is not building more features; it is watching someone like Leo or Alessio use a direct version of the agent without Taro as proxy.

## Approaches Considered

### Approach A: Living Project Brief MVP

Summary: Build the narrowest product around one promise: after every meeting or source drop, the agent proposes updates to a canonical project brief. Users approve, edit, or reject changes.

Effort: S
Risk: Low/Med

Pros:
- Sharpest wedge and easiest to explain.
- Directly tests whether users value controlled project memory.
- Avoids competing head-on with ClickUp or Notion as task and docs platforms.

Cons:
- May feel too narrow if users mainly want search and Q&A.
- Needs excellent source citations and diff/review UX.
- Does not yet solve full project operations.

Reuses:
- Canonical wiki.
- Pending edits.
- Source ingestion.
- Activity history.
- Leadabeelity repo-agent pattern.

### Approach B: Project Memory Q&A Copilot

Summary: Start with a shareable agent that answers project-history questions across meetings, emails, notes, and files, with citations. The living brief exists, but Q&A is the main UI.

Effort: S/M
Risk: Med

Pros:
- Closest to how Leo and Alessio already use the proxy workflow.
- Fastest route to "I asked and got an answer."
- Easier for users to understand than a memory review workflow.

Cons:
- More directly competes with ChatGPT, Claude, Notion AI, and ClickUp Brain.
- Risks becoming AI search over files.
- Memory formation may remain hidden and undervalued.

Reuses:
- Chat.
- Source retrieval.
- Project context.
- Citations.
- Existing advisor interface.

### Approach C: Consulting Delivery Workspace

Summary: Build a broader workspace for consulting PMs: living brief, Q&A, source library, tasks, decisions, handovers, status updates, and artifacts.

Effort: L/XL
Risk: High

Pros:
- Bigger long-term product vision.
- More complete replacement for fragmented consulting workflows.
- Can expand into artifacts, handovers, status reports, and team collaboration.

Cons:
- Too broad for pre-product validation.
- Risks becoming a weaker Notion or ClickUp clone with AI.
- Much harder to prove what users actually care about.

Reuses:
- Most of the current roadmap, but as later-stage architecture rather than the first market test.

## Recommended Approach

Proceed with Approach A: Living Project Brief MVP.

This is the most defensible wedge because it owns a job that general AI chat and workspace AI do not clearly own: keeping the official project understanding current from messy evidence, with human review and trust.

## Open Questions

- Will Leo or Alessio trust direct answers from the product without Taro acting as the proxy?
- Do users care more about the updated project brief itself or about asking questions against it later?
- Which source type creates the strongest first value: meeting transcripts, emails, notes, or deliverables?
- What should the first living brief contain: overview, stakeholders, decisions, open questions, action items, requirements, risks, or country/workstream views?
- How much review friction is acceptable after each meeting?
- Would a user pay for this as software, or only as a done-for-you memory setup/service at first?

## Success Criteria

For the next validation round:

- At least 2 non-founder users use the product or POC directly, without Taro proxying.
- A user uploads or provides a real meeting transcript and accepts at least one proposed project brief update.
- A user asks a project-memory question and says the answer saved them meaningful time versus searching or asking someone.
- A user identifies at least one source-backed answer they would not have trusted from plain ChatGPT.
- A user asks to use it again on another meeting or project.

Stronger commercial signal:

- A consulting PM, engagement manager, or delivery lead says they would pay, expense, or request budget for a living project brief maintained from their project history.

## Dependencies

- A direct-use demo or POC that Leo, Alessio, or a similar user can operate without Taro.
- A small set of real project inputs: transcripts, notes, emails, and existing deliverables.
- Source citations or traceability strong enough to make answers inspectable.
- A review flow where proposed memory updates can be accepted, edited, or rejected.

## The Assignment

Do not build a broader workspace next.

The concrete assignment is:

1. Pick one real recent Leadabeelity meeting transcript.
2. Run it through the current POC.
3. Produce proposed updates to a simple project brief.
4. Put Leo or Alessio in front of the output without explaining too much.
5. Ask them to accept, edit, reject, or challenge the updates.
6. Watch where they hesitate, what they trust, and what they ask next.

The goal is to learn whether the reviewable living brief is valuable on its own, not whether the whole product vision sounds good.

## What I Noticed

The strongest signal was not the original Capex-style idea. It was the fact that Taro already built a local agent for a real project and uses it intensely.

The second strongest signal was proxy usage: Leo and Alessio already ask project-memory questions, and some answers can be produced by directly forwarding the question to the agent.

The weakest part of the thesis is still ICP breadth. "Project managers on consulting teams" is too broad. The sharper initial user is a consultant or engagement manager coordinating multi-stakeholder, multi-workstream projects where memory failure creates client misalignment, missed follow-ups, and poor delivery.

The main strategic risk is that the product becomes AI search over files. The product should instead own the transition from messy evidence to official project memory.
